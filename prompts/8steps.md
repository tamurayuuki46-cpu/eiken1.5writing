## ① プラン(要件・設計)を作る ★人が関わる
```
.steering/_template/ をコピーして .steering/{YYYYMMDD}-{タスク}/ を作って。
{やりたいこと} について、書く前に私に質問して、答えをもとに requirements.md と design.md を埋めて。
決まっていない点は【要確認】として残して。やらないことも書いて。
```

## ② プランのレビュー(別セッション)
```
/clear 後、または別セッションで:
.steering/{YYYYMMDD}-{タスク}/ の requirements.md と design.md を、
design-reviewer と security-reviewer でレビューして。P0 は実装前に反映して。
```

## ③ テスト計画のレビュー
```
design.md のテスト方針と requirements.md の受入条件だけを edge-case-reviewer に見せて、
抜けている異常系・境界値を挙げて。
```

## ④ 実装
```
レビュー済みの design.md と tasklist.md だけを根拠に実装して。
プランに無い変更が必要になったら、止めて報告して。
```

## ⑤ テスト(tdd スキル)
```
tdd スキルに沿って進めて。先に失敗(Red)を確認し、最後に全通過の出力を見せて。
```

## ⑥ 実装の相互レビュー
```
design-reviewer・edge-case-reviewer・security-reviewer の3体で並列にレビューして。
P0・P1 があれば直して再レビュー。往復は最大4回で打ち切って、残りを報告して。
```

## ⑦ 人のレビューとPR
```
変更の設計判断と、間違えやすい箇所を説明して。判断はしないで、根拠がなければ「不明」と書いて。
問題なければ create-pr スキルでPRを作って。
```

## ⑧ 定期リファクタ(週次・月次)★人が関わる
```
先に全テストが通ることを確認して。そのうえで「{観点}」だけを対象に、{対象フォルダ} を整理して。
1変更ごとにテストを流し、失敗したら戻して。
観点は1回に1つ: SSoT違反 / 1ファイル1責務 / フォルダ構成 / ルール遵守 / テストの穴
```

## タスクの片付け
```
tasklist.md の「片付け」を進めて。decisions.md の長く残す決定は docs/ へ、
毎回守ることは .claude/rules/ へ移す案を出して。学びを CLAUDE.md の学びメモに1行追記して。
```

## 品質が揺れたとき(駆動 A.5.4)
```
最近の出力が不安定。X(CLAUDE.md・rules・docs の鮮度と矛盾)→ Y(テストの信頼性)→ F(モデル・実行の仕組み)の順に原因を調べて。
```
